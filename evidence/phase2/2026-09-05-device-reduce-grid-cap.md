# DeviceReduce grid 上限探索与复核（2026-09-05）

## 本轮结论

两批独立运行、每批三种顺序，共完成 54 条正式测量，每条 1000 个接受样本。没有发现 grid 达到上限或开始处理额外 tile 后持续的大幅性能陡降；发现一个更具体的待验证候选：**几乎满的残余 tile 比完整 tile 略慢**。

主候选：I32/I32 的 N=2,949,119 对比 N=2,949,120，六轮 median 差均为正，五轮相差约 2.048 微秒（2.817%），另一轮为 4.128 微秒（5.678%）。这不是已确认缺陷，不代表已实现 2.8% 优化；未修改 CUB、未生成优化版本、未提交公开 issue/PR。

## 假设与路径验证

当前 I32 策略为 256 threads/block、16 items/thread，tile=4096。实际日志中的第一阶段 kernel 最大驻留 block 查询结果为 6/SM；24 SM × 6 × subscription_factor 5 = 720 blocks 上限。这不是 profiler 实测占用率。

源码依据（相对 CCCL 工作副本）：

- `cub/cub/device/dispatch/dispatch_reduce.cuh:716`：查询最大驻留 block 数，形成 grid 上限。
- `cub/cub/grid/grid_even_share.cuh:118`：grid=`min(ceil(N/4096),720)`。
- 同文件 `:161`：实际 STRIP_MINE 的步长为 grid×4096。
- `cub/cub/agent/agent_reduce.cuh:431`：采用 STRIP_MINE；`:446` 的完整 tile 循环与 `:478` 的残余 tile 处理。
- `ConsumeFullTile` 支持向量化加载；`ConsumePartialTile` 使用带有效元素判断的标量式处理。这个代码差别提供假设，但本轮没有 kernel 内时间线或 SASS 对照，不能把所有时差归因于它。

三个中心值，各测 N-1、N、N+1：

| 中心 N | 三个规模 | 第一阶段 grid（日志确认） | N+1 的源码推导含义 |
|---:|---|---|---|
| 719×4096=2,945,024 | 2,945,023 / 2,945,024 / 2,945,025 | 719 / 719 / 720 | grid 首次到达 720 |
| 720×4096=2,949,120 | 2,949,119 / 2,949,120 / 2,949,121 | 720 / 720 / 720 | block 0 开始处理第二个 tile，仅 1 个有效元素 |
| 1440×4096=5,898,240 | 5,898,239 / 5,898,240 / 5,898,241 | 720 / 720 / 720 | block 0 开始处理第三个 tile，仅 1 个有效元素 |

所有规模均为两阶段归约。路径轮使用 `CCCL_EXPERIMENTAL_LOGGING=1 --profile`，只作路径证据，计时不用于性能判断。脚本在日志中核对 9 个 grid 值、256 threads、16 items/thread、vec_size=4 及 6 SM occupancy；不匹配则停止正式运行。

## 核心结果

主候选 N=2,949,120，GPU median 单位微秒：

| 批次/轮次 | N-1 | N | N+1 | (N-1)/N - 1 |
|---|---:|---:|---:|---:|
| 初测/升序 | 76.832 | 72.704 | 76.800 | +5.678% |
| 初测/降序 | 74.752 | 72.704 | 72.704 | +2.817% |
| 初测/移位 | 74.752 | 72.704 | 72.704 | +2.817% |
| 复核/升序 | 74.752 | 72.704 | 72.704 | +2.817% |
| 复核/降序 | 74.752 | 72.704 | 72.704 | +2.817% |
| 复核/移位 | 74.752 | 72.704 | 72.704 | +2.817% |

每轮配对计算：`(median(N-1)/median(N)-1)*100`，绝对差=`median(N-1)-median(N)`。没有跨批混配。相对样本标准差仍不可忽略，例如该 N-1 的六轮范围约 8.48–34.46%；方向一致不等于正式统计显著性或已排除系统误差。

其他两个中心的六轮配对概况：

| 中心 N | N-1 比 N 慢的轮数 | median 差范围 | 百分比范围 |
|---:|---:|---:|---:|
| 2,945,024 | 6/6 | +2.048 至 +13.312 微秒 | +2.817% 至 +18.310% |
| 5,898,240 | 6/6 | +1.024 至 +3.072 微秒 | +0.725% 至 +2.239% |

2,945,023 在两批升序轮都是第一个正式配置，且两次都明显更慢；这提示顺序/启动状态影响尚未排除，不能拿 +18% 作性能缺陷证据。全部数据均保留。N+1 相对 N 的方向不稳定或差为零，不支持“跨过 grid 上限必有稳定陡降”的结论。

## 为什么尚不能叫 bug

1. 几乎满的残余 tile 本来就可能走不同的加载/归约分支；更少元素不保证更短运行时间。
2. 官方 benchmark 每个 state 重新生成和分配输入，尚未做到同一地址、同一输入前缀仅改变有效长度。
3. 当前只有同一二进制的规模对照，没有“改变尾块处理、其余不变”的最小实现对照。
4. 保存的是汇总指标，不是样本级时间序列；未建立置信区间、误差下限或跨机器普适性。
5. 复核仍在同一次本机会话内，不是跨日期/重启/驱动版本验证。

## 下一步与停止条件

停止继续盲目扩大 grid 扫描，把主候选缩小为 N=2,949,120 附近的尾长度问题。下一阶段建议做一个项目内独立验证程序：分配一次固定输入，使用相同指针与前缀，只改变长度；先与可精确计算的参考和比较，再交错测量几种尾长度，仍不修改 CUB。这样能区分输入生成/地址影响与 CUB 路径本身。

若固定输入后差异消失或方向不再稳定，记录候选未通过，停止该方向；若仍存在，再检查对应 kernel 代码与上游已有方案，决定是否值得设计最小改动。未获证据前不谈 PR、不声称优化收益。
