- 原链接：[Compiler Explorer](https://godbolt.org/z/b8eTc1sTx)。网页读取失败，但公开只读 API `https://godbolt.org/api/shortlinkinfo/b8eTc1sTx` 成功返回完整源码和编译器配置。
- 源码 UTF-8 字节数 4053，SHA256 `d2de5d96499dc79068bc97083a5dc769b994a08c0e1be5fad14d0e860bdb1510`。
- 配置为 `nvcc133`，options 为空，没有执行面板。**不能由此推断报告者本地计时也没开优化**；我们必须显式使用 O3/sm89 并记录参数。
- 原程序数组长度 20000，值为连续整数；4096 个 block、每 block 256 线程。每个 block 都遍历全部 20000 个查询，并非将查询平均分给全 grid。总搜索数约 8192 万，输入数组仍仅约 160 KB。这是反复搜索、缓存复用的场景，不能描述为大数组流式访问。
- 每个 block 用 shared atomic 累计命中数，两个被比较的 kernel 都包含此开销。
- 原程序预热后测 10 次，报告最小值；先测手写再测库版本。没有读回命中计数核对结果，也没有完整检查 CUDA 错误。
- 后续不能直接把这个最小值比率作为性能结论：应补正确性/错误检查，交替顺序、多轮保存分布及环境；原程序用于建立同题联系，不当成已通过验证的 benchmark。

## 必须分开的两个因素

| 因素 | 原手写实现 | 库实现 | 后续控制方法 |
|---|---|---|---|
| 索引位宽 | `int` 的 lo/hi/mid | 指针迭代器的 difference_type | 先在同一 64 位宽度下比较算法，再以诊断对照检查 32 位影响 |
| 命中处理 | `v == query` 后直接结束 | 继续完成 lower_bound | 保持索引、输入和比较器语义一致，只改变能否在等价时结束 |

不能把两因素混合带来的总差距全归为提前退出，也不能直接给通用库的长度强制改成 int。讨论已指出运行时双分派会增加代码体积/编译成本；本阶段不采用这一条作为修复。

若考察通用比较器，等价关系应是 `!comp(a,b) && !comp(b,a)`，不能直接使用 `==` 替代。算法允许符合规定分区条件的范围，不限于全局排序数组。必须保留正反比较、迭代器能力、重复值、空范围等契约，不能因为整数有序数组测试通过就宣称通用实现正确。

初始性能场景至少区分：命中值分散、全部未命中、集中命中首个中点；最后一种偏向提前退出，只能作为特定分布证据，不能用它的倍数代表一般工作负载。还需后续验证混合查询、重复值与回归；不假设多一个比较在 GPU 分支分歧下必然更快。
